# 一、Java 并发与多线程

## 1. 线程和进程的区别(3)

- **进程**：正在运行的程序的实例，包含一个或多个线程
    
- **空间隔离**：不同进程使用不同内存空间；同一进程内的线程共享进程空间（包括 代码段 打开的文件 全局资源 ）。
    
- **线程更轻量**：线程上下文切换成本相对更低(进程切换 需要切换成个地址 还有执行进度 然后 线程有程序计数器 只需要换执行进度)。
    
操作系统
  └── 进程（Java 进程）
        └── JVM 实例 ——运行的时候管理 线程
              ├── 堆
              ├── 方法区/元空间
              ├── 线程栈
              └── 执行引擎
## 2. 并行和并发的区别(宏观微观)

- **并发**：同一时间轮流做多件事，多个线程轮流使用一个或多个 CPU。
    
- **并行**：同一时间同时做多件事，例如 4 个 CPU 同时执行 4 个线程。
`` 单核处理器 不能 并行 
 `多核处理器 可以 并发
## 3. 线程的创建方式 (本质)

1. 继承 `Thread` 类
    
2. 实现 `Runnable` 接口
    
3. 实现 `Callable` 接口
    
4. 使用线程池创建线程==🟢（**复用**）
   
**本质：构造 线程 对象 调用start（）**

## 4. Runnable 和 Callable 的区别(异常 返回结果)

`Callable` 有返回值、能抛异常，配合 `Future` 拿结果

## 5. run() 和 start() 的区别 （逻辑 启动新的）

- **`run()`：任务逻辑，可多次调；直接调不开新线程，就在当前线程跑。***（不启动新线程的话 就是主线程运行）
    
- **`start()`：启动新线程，只能一次；新线程起来后由 JVM 调 `run()`。**
    

## 6. 线程状态变化(6)


**新建 - 可运行 - 阻塞 - 有限等待 - 无限等待 - 终止**

| 状态              | 含义       | 如何进入                                            | 如何离开                                  |
| --------------- | -------- | ----------------------------------------------- | ------------------------------------- |
| `NEW`           | 已创建未启动   | `new Thread()`                                  | 调用 `start()` → `RUNNABLE`             |
| `RUNNABLE`      | 可运行/正在运行 | `start()`、被唤醒、获得锁                               | 被阻塞、等待、结束                             |
| `BLOCKED`       | 等待监视器锁   | 竞争 `synchronized` 锁失败                           | 获得锁 → `RUNNABLE`                      |
| `WAITING`       | 无限期等待    | `Object.wait()`、`join()`、`LockSupport.park()`   | `notify/notifyAll`、目标线程结束、`unpark`、中断 |
| `TIMED_WAITING` | 限时等待     | `sleep(ms)`、`wait(ms)`、`join(ms)`、`parkNanos()` | 超时、通知、中断、`unpark`                     |
| `TERMINATED`    | 已终止      | `run()` 结束或异常退出                                 | 不可再变                                  |

简化理解：新建 → 运行 → 销毁，中间可能等待锁、无限期等待、有限等待。

## 7. 线程如何按顺序执行(join 单线程池)

- 使用 `join()`。
    
- 例如 `t1.join()`：等待 `t1` 运行完，当前线程才能继续往下执行。
    

## 8. notify(通知) 和 notifyAll 的区别

- `notify()`：随机唤醒一个等待线程。
    
- `notifyAll()`：唤醒全部等待线程。
    

## 9. wait 和 sleep 的区别(5)

| 对比   | sleep         | wait                      |
| ---- | ------------- | ------------------------- |
| 所属类  | `Thread` 静态方法 | `Object` 实例方法             |
| 锁    | 不释放锁，抱着锁睡     | 释放锁，让别人进来                 |
| 调用条件 | 任何地方都能调       | 必须在 `synchronized` 块/方法里调 |
| 唤醒   | 时间到自动醒        | 需要 `notify/notifyAll` 或超时 |
| 醒后状态 | 就绪，等 CPU 调度   | 先抢锁，抢到才继续                 |


## 10. synchronized 底层原理（monitor）


==🔵**每个对象都有“当锁的资格”**

`1.6之前只有重量级锁 1.6之后进行了升级

- 底层核心是 **monitor 监视器**。
    
- 关键结构：
    
    1. `WaitSet`：等待小房间
        
    2. `EntryList`：阻塞队列
        
    3. `Owner`：拥有锁的线程
        
- 这些都是围绕线程竞争锁设计的。
    

## 11. 锁升级(1 少 多)

`从上到下 一步步的升级

- **偏向锁**：只有一个线程使用锁，无竞争，靠对象头记线程 ID，直接放行。
    
- **轻量级锁**：少量线程交替获取锁，用 CAS + 自旋处理，避免直接进内核阻塞。
    
- **重量级锁**：monitor 重量级锁，涉及用户态和内核态切换，成本高、性能低。
    

## 12. JMM（Java 内存模型 并发特性）


 **happens-before** 和 **锁**

1. 定义多线程之间共享内存读写操作的行为规范。
    
2. JMM 把内存分为：
    
    - 线程私有内存
        
    - 所有线程共享的主内存
        
3. 线程之间相互隔离，通过主内存进行交互。
    

## 13. CAS（比较再交换，乐观锁）

- 使用操作系统提供的原子操作，一般由 C/C++ 实现。
    
- 语义是“单地址条件更新”：比较内存值是否等于预期值，相等则更新。
    
- 局限：只能操控一个节点；涉及多个地址时无能为力。
    
- 硬件实现上，单字原子容易，多地址原子代价高。
    

## 14. volatile 的理解(CPU JIT)

- CPU 和 JIT 为了优化性能可能做：
    
    1. 指令重排序
        
    2. 优化代码
        
- `volatile` 用于保证可见性和一定程度的有序性，禁止相关重排序。
    

## 15. AQS(核心)

- Java 语言实现的悲观锁基础框架，需要手动开启和关闭。
    
- 同时提供多种锁竞争解决方案。
    
- 使用 FIFO 先进先出队列。
    
- 通过 CAS 保证不被同时抢，公平锁基于此实现。
    

## 16. ReentrantLock 实现原理

- 基于 **CAS + AQS**。
    
- 是可重入锁。
    
- 支持公平锁和非公平锁，默认非公平。
    

## 17. synchronized 和 Lock 的区别

1. `synchronized` 由 C++/JVM 实现，自动释放；`Lock` 需要手动 `unlock()` 释放。
    
2. 两者都支持悲观、互斥、可重入；`Lock` 额外支持公平、可打断、超时。
    
3. 没有竞争时 `synchronized` 做了优化，表现不错；竞争激烈时 `Lock` 往往性能更好。
    

## 18. 死锁产生的条件与诊断

- 一个线程需要同时获取多把锁时，容易发生死锁。
    
- 诊断命令：
    
    1. `jps`：输出进程状态信息
        
    2. `jstack`：查看线程堆栈信息
        
- 可视化工具：`jconsole`、`VisualVM` 可检查死锁。
    

## 19. ConcurrentHashMap

### JDK 1.7

- 链表 + 数组
    
- 内含 `ReentrantLock`
    
- 长度固定 16
    

### JDK 1.8

- 数组 + 链表 + 红黑树
    
- 新增 CAS 控制添加数组节点
    
- 用 `synchronized` 锁住当前链表或红黑树的首节点，性能也不低
    
- CAS 局限：只能操控一个节点，涉及多个节点时无能为力
    

## 20. 并发程序出现问题的根本原因(三大特性)

1. **原子性**：完整操作不可分割，可用 `synchronized` 或 `Lock` 保证。
    
2. **可见性**：一个线程修改共享变量，另一个线程能看见，可用 `volatile`。
    
3. **有序性**：JIT 编译 class 文件时重排、CPU 执行代码时重排，可用 `volatile` 限制。
    

## 21. 线程池（7个参数）

### 核心参数

- 核心线程数目
    
- 最大线程数目 = 核心线程数目 + 救急线程最大数目
    
- 生存时间：释放救急线程
    
- 时间单位
    
- 阻塞队列：核心线程满了进入这里，这里满了产生救急线程，FIFO
    
- 线程工厂：定制名字、是否为守护线程
    
- 拒绝策略：全部满了时触发，默认抛出异常
    

### 执行原理

核心线程 → 阻塞队列 → 最大线程 → 拒绝策略。

### 如何确定核心线程数

设 `n` 为 CPU 核数：

- IO 密集型任务：`2n + 1`
    
- CPU 密集型任务：`n + 1`，避免频繁切换，减少线程数
    

### 线程池种类

1. **固定线程数线程池**：没有临时线程，最大容量默认 `Integer.MAX_VALUE`，适合知道需要多少线程、任务耗时可控的场景。
    
2. **单线程线程池**：只有一个线程，没有临时线程，最大容量默认 `Integer.MAX_VALUE`，适合按顺序执行的任务。
    
3. **可缓存线程池**：全都是核心线程执行，任务数密集、执行时间短。
    

### 使用场景

- 批量异步任务
    
- 控制并发数量
    
- 任务排队与拒绝保护
    
- 定时/延迟任务等
    

## 22. CountDownLatch

- `await()` 等待其他线程完成，然后再进行最后操作。
    
- 相当于并行操作后的汇合点。
    

## 23. ThreadLocal 概述

- 为每个线程分配独立的线程副本，解决并发访问冲突。
    
- 强引用：怎么都不会回收。
    
- 软引用：GC 会回收。

## 10. ArrayList

1. 从 1 开始算，寻址公式需要 `(i - 1) * 存储数据类型大小`，增加一个指令，性能相对从 0 开始低一些。
    
2. 查询快，增删慢；链表相反。
    
3. 成员变量属于类内部，静态变量也属于成员变量的一种。
    
4. 创建：
    
    - 有初始容量：按指定容量创建。
        
    - 没有初始容量：根据默认值创建 10 大小的数组，懒加载。
        
5. 扩容：`new = old + old >> 1`，即约 1.5 倍。
    
    - 好处：折中，位运算更快，右移相当于 `/2`，然后拷贝。
        
6. 底层实现：
    
    - 数组
        
    - 初始 0，添加后为 10
        
    - 扩容为 1.5 倍
        
    - 添加：先计算容量，够则直接添加，不够再扩容，返回布尔
        
7. 数据和 List 转化：
    
    - `asList`：指针引用
        
    - `toArray`：新对象
        

## 11. LinkedList

### ArrayList 和 LinkedList 区别

1. 数据结构：动态数组 / 双向链表
    
2. 操作数据效率：查询、新增、删除不同
    
3. 空间占用不同
    
4. 线程安全：都不安全；想保证可用局部变量或 `synchronized` 包装
    

补充：ArrayList 需要扩容 1.5 倍，LinkedList 不需要。

## 12. HashMap

### 实现原理

1. 散列表：数组 + 链表 / 红黑树
    
2. key 相同，覆盖原始值
    
3. key 不同但哈希冲突，放入链表或红黑树
    
4. 获取时计算 hash，判断 key 是否相同
    

版本差异：

- JDK 1.8 之前：没有红黑树
    
- JDK 1.8 之后：有红黑树；扩容后红黑树节点小于等于 6 个，退化成链表
    

### put 方法具体流程

1. 懒加载，0.75 是时间空间最合适的权重，冲突多了查询慢
    
2. 判断是否初始化，未初始化则初始化
    
3. 计算 hash 索引
    
4. 当前位置没有数据，直接新增
    
5. 新增时考虑是否大于 0.75，准备扩容
    
6. 新增位置已有数据，判断 key 是否一样，一样就覆盖
    
7. 判断是红黑树还是链表：
    
    - 链表：判断 key 是否存在，存在覆盖；不存在再判断是否大于等于 8
        
    - 链表和红黑树都需要判断是否重复 key
        

### HashMap 扩容

- 初始化：懒加载 16
    

流程：

1. 变长一倍
    
2. 新建数组
    
3. 遍历旧数组：
    
    - 只有一个节点
        
    - 红黑树
        
    - 链表
        
4. 计算新位置：
    
    - 无变化：原位置
        
    - 有变化：原位置 + 老的长度
        

### HashMap 寻址算法

1. `>>>` 让 hash 值更均匀，减少 hash 冲突，让高位参与运算
    
2. `(n - 1) & hash` 效率高，不用取模
    
    - 原理：保留 hash 的低 k 位，其他位清零
        

### HashMap 数组长度一定是 2 的次幂

1. 计算索引效率更高
    
2. 扩容时计算新索引更方便
    

### HashMap 多线程死循环

- JDK 1.7 之前使用头插法，新来的在头上，很反直觉。
    
- 关键词：`e`、`next`
    
- 两个线程的 `e` 和 `next` 来回绕，最终形成 `b -> a`，然后新来的 `a` 覆盖 `a`，导致 `b` 被 `a` 指向的同时又指向 `a`。

# 三、JVM

## 1. JVM 运行时数据区

JVM 运行时数据区包括：

- 方法区
    
- 堆
    
- 虚拟机栈
    
- 本地方法栈
    
- 程序计数器
    

线程私有/共享：

- **共享**：方法区、堆
    
- **线程私有**：虚拟机栈、本地方法栈、程序计数器
    

## 2. 堆和栈的区别

|对比|堆|栈|
|---|---|---|
|线程共享|共享|线程私有|
|存放内容|对象实例和数组|方法调用的栈帧：局部变量表、操作数栈等|
|生命周期|由 GC 管理|随方法调用和返回入栈出栈|

## 3. 怎么判断对象可回收？GC Roots 有哪些？

- 使用**可达性分析**：从 GC Roots 出发不可达的对象才可回收。
    
- GC Roots 包括：
    
    - 虚拟机栈中引用的对象
        
    - 方法区静态属性引用的对象
        
    - 常量引用的对象
        
    - 本地方法栈 JNI 引用的对象等
        

## 4. 常见 GC 算法

常见 GC 算法：

1. 标记
    
2. 清除
    
3. 复制
    
4. 标记整理
    
5. 分代收集
    

为什么新生代用复制、老年代用标记整理：

- 新生代对象朝生夕死、存活少，适合复制算法。
    
- 老年代对象存活率高，适合标记整理或标记清除，减少复制开销。
    

## 5. Minor GC / Full GC 触发时机与对象进入老年代

### Minor GC 触发

- 新生代 Eden 满时触发。
    

### Full GC 常见触发

1. 老年代空间不足
    
2. 空间分配担保失败
    
3. 元空间不足
    
4. 显式调用 `System.gc()`
    

### 对象进入老年代

1. 对象经历多次 Minor GC 达到年龄阈值
    
2. 大对象直接进老年代
    
3. 动态年龄判定或空间分配担保时进入老年代
    

## 6. CMS 和 G1

### CMS

- 标记清除式并发收集器
    
- 流程：初始标记 → 并发标记 → 重新标记 → 并发清除
    
- 追求低停顿
    
- 有浮动垃圾和碎片问题
    

### G1

- 面向 Region 的分代收集器
    
- 流程：初始标记 → 并发标记 → 最终标记 → 筛选回收
    
- 可预测停顿，支持整理，适合大堆

# 四、MySQL 数据库

## 1. MVCC 隔离性的原理

基础概念：

- **缓冲池**：直接操作缓存到内存中的数据，减少磁盘 IO。
    
- **IO**：先切换，然后搜索（最慢），最后拷贝。
    
- **数据页**：数据的最小单元。
    
- **redo log**：重做日志，记录事务提交时数据的修改，用来实现事务持久化。
    
- **undo log**：记录数据被修改前的数据，提供回滚和 MVCC，是逻辑日志，帮助实现事务一致性和原子性。
    
- 锁和 MVCC 保证隔离性。
    

MVCC：多版本并发控制

1. 隐藏字段：操作 id、记录地址
    
2. undo log：版本链
    
3. ReadView 解决一个事务查询选择哪个版本：
    
    - 隔离级别不同
        
    - RC：每一次快照
        
    - RR：第一次快照
        

## 2. 数据库事务 ACID 特性

1. **原子性**：要么全做，要么全部失败。
    
2. **一致性**：事务整个过程加上业务逻辑后，保证约束条件都得到满足，确保正确性和一致性。
    
3. **隔离性**：保证一个事务同一时刻只能够一个线程修改，保证可见性和互相影响程度；不隔离好会出现脏读、幻读、不可重复读，MVCC 多版本并发控制。
    
4. **持久性**：保证断电事故后数据不丢失、损坏可写日志记录操作，保证提交后持久性。
    

## 3. MySQL 存储引擎

存储引擎 = 数据怎么存、怎么读、怎么保证不坏的模块。  
MySQL 存储引擎是插件式，不同表可以用不同存储引擎，适应不同场景。

|特性|InnoDB|MyISAM|
|---|---|---|
|事务|事务型|非事务型|
|并发|行级锁|表级锁|
|外键|支持|不支持|
|备份|在线热备|不支持|
|崩溃恢复|概率低|慢、易丢失|
|其他|聚簇索引、MVCC|压缩表、空间数据索引|

MVCC：有新旧版本，读正在改写的版本时会使用旧版本。

## 4. 数据库事务隔离级别

问题定义：

- **脏读**：看到别人没有提交的数据，或者回滚的数据，最不能忍耐。
    
- **不可重复读**：同一事务内前后两次读，被被人修改了。
    
- **幻读**：同一事务内前后两次读，多了几行，莫名其妙。
    

隔离级别：

1. **读未提交**：什么都管不住。
    
2. **读已提交**：只防脏读。
    
3. **可重复读**：默认，防脏读 + 防不可重复读。
    
4. **串行化**：全防，但最慢。
    

## 5. 索引查询快的原因

1. 读的层数很少
    
2. 有序，支持二分查找
    
3. 关键词多的话不用回表
    
4. 索引页内存小，容易缓存
    

## 6. 索引的种类

### 物理角度

- **聚簇索引**：记录唯一的同时附带数据
    
- **非聚簇索引 / 二级索引**：只有唯一
    

### 逻辑角度

- 唯一索引
    
- 普通索引
    
- 主键索引
    
- 联合索引
    

### 数据角度

- B+ 树：5 阶，每个节点存 4 个 key
    
- Hash 索引
    

### B 树和 B+ 树

- B 树和 B+ 树都是平衡搜索树；B+ 树所有数据都在尾部叶子节点。
    
- B+ 树优点：
    
    1. 读取的数据少
        
    2. 查询更稳定
        
    3. 方便扫库和区间查询
        

## 7. 索引哪些条件会失效

1. **对索引列做运算或函数**  
    `WHERE id + 1 = 10`、`WHERE YEAR(create_time) = 2024`  
    改成：`WHERE id = 9`、`WHERE create_time >= '2024-01-01' AND create_time < '2025-01-01'`
    
2. **隐式类型转换**  
    `WHERE phone = 13800138000`，phone 是字符串列却用数字查。  
    改成：`WHERE phone = '13800138000'`
    
3. **前导模糊匹配**  
    `WHERE name LIKE '%张'` 或 `LIKE '%张%'`  
    能用索引：`LIKE '张%'`
    
4. **联合索引不满足最左前缀**  
    索引 `(a, b, c)`，查 `WHERE b = 1` 或 `WHERE c = 1` 用不上。  
    能用：`WHERE a = 1`、`WHERE a = 1 AND b = 2`、`WHERE a = 1 AND b = 2 AND c = 3`
    
5. **范围查询断了后面的列**  
    索引 `(a, b)`，`WHERE a > 1 AND b = 2`，a 是范围，b 用不上索引排序。
    
6. **OR 两边有一边没索引**  
    `WHERE a = 1 OR b = 2`，b 没索引，可能全表扫。  
    改成：两边都建索引，或改用 `UNION`。
    
7. **使用 `!=`、`NOT IN`、`NOT LIKE`、`IS NOT NULL`（视情况）**  
    否定条件通常要扫大部分行，大概率不走索引。
    
8. **优化器觉得全表扫更便宜**  
    表很小、返回大部分行、索引区分度太低，优化器主动放弃索引。
    

## 8. MySQL 优化方案

1. **慢查询日志 + EXPLAIN**：看 `type` 访问方式、`key` 是否用索引、`rows` 扫描行数、`extra` 是否回表。
    
2. **SQL 和索引**：减少字段，不要用错误 SQL；字符串用数字查会导致索引失效。
    
3. **建错索引**：检查索引设计。
    
4. **表结构**：合理设计字段和表。
    
5. **配置 / 服务器优化**。
    
6. **架构**：分库分表、读写分离。
    

## 9. SQL 优化方案

1. 慢查询日志
    
2. 优化 SQL 写法
    
3. 索引优化
    
4. 看执行计划 `EXPLAIN`

# 五、Redis 与缓存

## 1. 缓存三兄弟

### 穿透

- 布隆过滤器：需要预热 bitmap 01 hash 值，只需要知道有还是没有，有可能误判。
    
- 空值缓存：前后缓存不一致，大量 null。
    

### 击穿（一个热点 key）

- 互斥锁：查数据库的时候加锁，强一致、低效。
    
- 逻辑过期：查询缓存的逻辑缓存时间，过期获得锁不让人查旧数据，高可用。
    

### 雪崩（大量小 key）

- 随机 TTL
    
- 多级缓存
    
- 限流降级
    
- 集群
    

## 2. 双写一致

数据库和 Redis 都需要进行一致性的修改。

### 读

命中返回，未命中查询数据库，返回。

### 写

延迟双删：改的时候同时间读写会有问题。  
延时：为了服从主从同步。

### 双写一致方案

- 读写锁：读写拿一样的锁
    
    - 共享锁：可以读
        
    - 排他锁：其他线程的读写都不行
        
- 异步通知
    
    - MQ：发通知
        
    - Canal：监听日志
        

## 3. 持久化

### RDB

- 数据备份，数据快照。
    

### AOF

- 记录所有 Redis 的写命令。
    
- 指定命令重写。
    

## 4. 删除策略（两者都要）

### 惰性删除

- 使用的时候才会去检查，对内存不好。
    

### 定期删除

- 对一定量的 key 检查：1 SLOW，2 FAST。
    

## 5. 数据淘汰策略

默认是内存满了就不添加新的了。

|策略|范围|算法|说明|
|---|---|---|---|
|`allkeys-lru`|所有 Key|LRU 最近最少使用|通用缓存最常用，保留最近被访问过的热点数据|
|`allkeys-lfu`|所有 Key|LFU 最不经常使用|访问频次冷热分明，能避免偶发全表扫描“欺骗”LRU|

## 6. 分布式锁

- 集群环境下的多线程并发，需要分布式锁。
    
- 底层是 `setnx` 和 `lua` 脚本。
    

## 7. 主从同步

- 一主多从：主节点写，从节点读。
    
- 主从 + 哨兵模式：解决高并发、高可用。
    

## 8. 脑裂

相当于出现两个主。网络错误时，老主清空，用新主的。

解决办法：

1. 设置最少的从节点数。
    
2. 同步延迟不超过 5s。如果从节点落后太多，比如超过 5 秒没确认，主节点认为“没有合格从节点”，于是拒绝写。
    

## 9. 分片

- 分片可以通过哈希值，解决海量存储。
    
- 将数据按哈希分散到多个节点，突破单机内存和容量限制。

# 六、Spring / SpringMVC / SpringBoot

## 1. Bean 线程安全

结论：**Bean 不是线程安全的**。

- 成员变量需要考虑线程安全。
    
- 局部变量不需要，因为局部变量是每个线程私有的。
    
- 无状态、不能修改的类是绝对线程安全的。
    
- 如果在 Bean 定义里加入可修改的成员变量，需要考虑是否线程安全。
    

## 2. 什么是 AOP，怎么使用

定义：面向切面编程，拦截器思想，抽取重复，降低耦合。

场景：

1. **记录操作日志**：使用 AOP 中的环绕通知 + 切点表达式，记录参数保存数据库。
    
2. **Spring 事务**。
    

## 3. 事务失效的场景

1. 异常被捕获处理，自己处理了，事务不管。
    
2. 抛出检查异常，需配置 `rollbackFor = Exception.class`。
    
3. 非 public 方法，添加事务通知前提条件是 public。
    

## 4. Bean 的生命周期

1. 通过 `BeanDefinition` 获取 Bean 的定义信息
    
2. **实例化**：调用构造方法创建 Bean 对象（空的）
    
3. **属性注入**：注入 `@Autowired`、`@Value` 等依赖
    
4. 处理 `Aware` 接口
    
5. **初始化前**：执行初始化前的扩展处理
    
6. **初始化**：执行 `@PostConstruct`、`afterPropertiesSet()`、自定义初始化方法
    
7. **初始化后**：执行初始化后的扩展处理，AOP 代理通常在这里生成
    
8. **使用**：Bean 可以被业务代码使用
    
9. **销毁**：容器关闭时执行 `@PreDestroy`、`destroy()`、自定义销毁方法
    

简化流程：

1. `BeanDefinition`（构造函数）
    
2. 依赖注入
    
3. Aware 接口
    
4. `BeanPostProcessor` 前置
    
5. 初始化方法
    
6. `BeanPostProcessor` 后置
    
7. 使用
    
8. 销毁
    

## 5. Spring 中的循环引用

- `@Lazy` 延迟缓存
    
- 三级缓存：
    
    - 一级缓存：缓存实例
        
    - 二级缓存：缓存半成品，生命周期没走完
        
    - 三级缓存：缓存 Bean 工厂，解决增强的代理对象
        

## 6. SpringMVC 的执行流程

1. 浏览器/前端发请求
    
2. `DispatcherServlet` 接收请求
    
3. `HandlerMapping` 根据 URL 找到对应的 Handler（Controller 方法）
    
4. `HandlerAdapter` 负责调用这个 Handler
    
5. `HandlerAdapter` 解析参数（`@RequestParam`、`@PathVariable`、`@RequestBody` 等）
    
6. 执行 Controller 方法，得到返回值
    
7. 返回值处理：
    
    - 传统 MVC：`ModelAndView` → `ViewResolver` → 渲染 JSP/模板
        
    - 前后端分离：`@ResponseBody` / `@RestController` → `HttpMessageConverter`
        
8. `HttpMessageConverter` 把对象转成 JSON（如 Jackson）
    
9. 写入 `HttpServletResponse` 响应体
    
10. 前端收到 JSON，自己渲染页面
    

## 7. SpringBoot 自动配置原理

流程：

1. `@SpringBootApplication`
    
2. 包含 `@EnableAutoConfiguration`
    
3. `@Import(AutoConfigurationImportSelector.class)`
    
4. 读取自动配置清单：
    
    - Spring Boot 2.7 前：`META-INF/spring.factories`
        
    - Spring Boot 3.x：`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`
        
5. 得到一堆自动配置类，如 `DataSourceAutoConfiguration`
    
6. 逐个用 `@ConditionalOn...` 判断是否生效
    
7. 生效的配置类注册对应的 Bean
    
8. 用户自己定义的 Bean 优先，自动配置退让

# 七、高频对比速查表

## 1. 线程 vs 进程

- 进程有独立空间；同进程线程共享空间。
    
- 线程更轻，切换成本低。
    

## 2. 并发 vs 并行

- 并发：轮流做。
    
- 并行：同时做。
    

## 3. Runnable vs Callable

- Callable 有返回值、可抛异常、配合 Future。
    

## 4. run vs start

- `run` 是普通方法，可多次调用。
    
- `start` 开线程，只能一次。
    

## 5. wait vs sleep

- `wait` 属于 Object，释放锁，必须在 synchronized 中。
    
- `sleep` 属于 Thread，不释放锁。
    

## 6. synchronized vs Lock

- 自动释放 vs 手动释放。
    
- Lock 支持公平、可打断、超时；竞争激烈时往往更好。
    

## 7. String vs StringBuffer vs StringBuilder

- String 不可变。
    
- StringBuffer 线程安全。
    
- StringBuilder 非线程安全、性能高。
    
- 按“是否拼接、是否多线程、是否作为 key/常量/日志/共享变量”选择。
    

## 8. 接口 vs 抽象类

- 接口偏 can-do，可多实现。
    
- 抽象类偏 is-a，单继承，可有字段和构造器。
    

## 9. `==` vs `equals`

- `==` 比较地址/基本类型值。
    
- `equals` 默认地址，重写后比内容；重写 equals 必须重写 hashCode。
    

## 10. ArrayList vs LinkedList

- 动态数组 vs 双向链表。
    
- 查询快增删慢 vs 查询慢增删快。
    
- ArrayList 扩容约 1.5 倍，LinkedList 不需要。
    

## 11. InnoDB vs MyISAM

- InnoDB：事务、行锁、外键、热备、崩溃恢复好、聚簇索引、MVCC。
    
- MyISAM：非事务、表锁、无外键、压缩表。
    

## 12. 事务隔离级别

- 读未提交：什么都管不住。
    
- 读已提交：防脏读。
    
- 可重复读：默认，防脏读 + 不可重复读。
    
- 串行化：全防，最慢。
    

## 13. Error vs Exception

- Exception 程序级、可处理。
    
- Error 系统/JVM 级、一般不可恢复。
