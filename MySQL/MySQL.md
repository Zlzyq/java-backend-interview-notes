
# MVCC 隔离性的原理

缓冲池：直接操作缓存到内存中的数据 减少磁盘IO操作 

IO：先切换 然后 搜索（最慢）最后拷贝

数据页：数据 最小单元

redo log : 重做日志 记录事务提交的时候 数据的修改 然后 用来实现事务的持久化

undo log:记录 数据被修改前的数据 提供回滚和 MVCC （逻辑日志） 帮助实现 事物的一致性 和原子性

锁和 MVCC 保证的是 隔离性

**MVCC**：多版本并发控制 

1. 隐藏字段：操作id 记录地址
2. undo log：版本链 
3. reaView 解决 一个事务查询选择版本呢：隔离级别不同 RC  每一次快照 RR第一次快照

# 数据库事物的ACID特性 

1. **原子性** 要么全做 要么全部失失败
   
2. **一致性** 事务的整个过程 业务逻辑加上之后 保证 约束条件都得到满足 确保 正确性和一致性
   
3. **隔离性** 保证 一个事务 同一时刻只能够一个线程修改 保证可见性和互相影响的程度 如果不隔离好 会脏读幻读 不可重复读（MVCC:多版本并发控制）
   
4. **持久性** 保证断电事故 然后数据不丢失 损坏可以写日志记录操作 保证提交后的 就有持久性

# 数据库的事务隔离级别

脏读 ： 看到别人没有提交的数据 或者 回滚 (最不能忍耐 递减)

不可重复度 ： 同一事务内 前后两次读的时候 被被人修改了

幻读 ： 同一事务内 前后两次读的时候  多了几行 莫名其妙


1. **读未提交**（Read Uncommitted） 什么豆管不住
2. **读已提交**（Read Committed）：只防脏读
3. ==🔴默认 **可重复读**（Repeatable Read）：防脏读 + 防不可重复读
4.  **串行化**（Serializable）：全防，但最慢

# 索引哪些条件会失效

**1. 对索引列做运算或函数**  
`WHERE id + 1 = 10`、`WHERE YEAR(create_time) = 2024`  
→ 数据库得对每一行算一遍，没法按索引顺序找。  
**改成：** `WHERE id = 9`、`WHERE create_time >= '2024-01-01' AND create_time < '2025-01-01'`

**2. 隐式类型转换**  
`WHERE phone = 13800138000`（phone 是字符串列，却用数字查）  
→ 数据库把列转成数字再比，等于对列做了函数，索引失效。  
**改成：** `WHERE phone = '13800138000'`

**3. 前导模糊匹配**  
`WHERE name LIKE '%张'` 或 `LIKE '%张%'`  
→ 前面带 `%`，像电话簿不知道姓只知名字，没法定位。  
**能用索引：** `LIKE '张%'`

**4. 联合索引不满足最左前缀**  
索引 `(a, b, c)`，你查 `WHERE b = 1` 或 `WHERE c = 1`  
→ 跳过了最左列 a，排序顺序用不上。  
**能用：** `WHERE a = 1`、`WHERE a = 1 AND b = 2`、`WHERE a = 1 AND b = 2 AND c = 3`

**5. 范围查询断了后面的列**  
索引 `(a, b)`，`WHERE a > 1 AND b = 2`  
→ a 是范围，b 在 a 相同的前提下才有顺序，a 一变范围，b 就用不上索引排序（但 a 本身还能用）。

**6. OR 两边有一边没索引**  
`WHERE a = 1 OR b = 2`，b 没索引  
→ 数据库干脆全表扫。  
**改成：** 两边都建索引，或改用 `UNION`。

**7. 使用 `!=`、`NOT IN`、`NOT LIKE`、`IS NOT NULL`（视情况）**  
→ 这些是否定条件，通常要扫大部分行，优化器觉得全表扫更划算，就不走索引。不是绝对失效，但**大概率不走**。

**8. 优化器觉得全表扫更便宜**  
表很小、或查询要返回大部分行、或索引区分度太低（比如性别列只有男/女）  
→ 走索引要回表很多次，不如直接全表扫。**这不是“失效”，是优化器主动放弃**
