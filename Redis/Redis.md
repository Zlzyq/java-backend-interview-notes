# 缓存三兄弟

## 穿透

- 布隆过滤器（需要预热 bitmap 01 hash值 只需要知道有还是没有 有可能误判）
    
- 空值缓存（前后缓存不一致，大量 null）
    

## 击穿（一个热点 key）

- 互斥锁（查数据库的时候加锁 - 强一致 低效）
    
- 逻辑过期（查询缓存的逻辑缓存时间 过期获得锁不让人查旧数据 高可用）
    

## 雪崩（大量小 key）

- 随机 TTL、多级缓存、限流降级 集群

# 双写一致

数据库和 Redis 都需要进行一致性的修改。

## 读

命中返回，未命中查询数据库，返回。

## 写

延迟双删（改的时候 同时间读写会有问题）

- 延时：为了服从主从 同步
    

## 双写一致方案

- 读写锁（读写拿一样的锁）
    
    - 共享锁（可以读）
        
    - 排他锁（其他线程的读写都不行）
        
- 异步通知
    
    - mq（发通知）
        
    - canal（监听日志）

# 数据淘汰策略

默认是内存满了就不添加新的了。

|策略|范围|算法|说明|
|---|---|---|---|
|`allkeys-lru`|**所有 Key**|**LRU**（最近最少使用）|**通用缓存最常用**。希望保留最近被访问过的热点数据。|
|`allkeys-lfu`|**所有 Key**|**LFU**（最不经常使用）|访问频次冷热分明，能避免偶发的全表扫描“欺骗”LRU。|

# 主从同步

- 一主多从：主节点写，从节点读。
    
- 主从 + 哨兵模式：解决高并发、高可用。
    

## 脑裂

相当于出现两个主。网络错误，老主人清空，用新主人的。

解决办法：

1. 最少的从节点为
    
2. 同步不延迟不超过 5s。如果从节点落后太多，比如超过 5 秒没确认，主节点也认为“没有合格从节点”，于是拒绝写。
